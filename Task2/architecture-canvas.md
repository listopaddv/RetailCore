# Architecture Canvas RetailCore

Текущее состояние платформы.

Источники: кейс, исходная схема AS-IS, три интервью с разработчиками, фрагмент OrderProcessingService.java. Цели и ожидания также взяты из интервью бизнеса и поддержки.

## Архитектурный контекст

| Блок | Содержание |
| --- | --- |
| Ценность для бизнеса | Оформление и выполнение заказов из разных каналов. Цели изменений: устойчивость заказного процесса, более быстрый выпуск функций и понятные данные. В перспективе нужны персонализация, гибкие предложения и новые партнёры |
| Ключевые участники | Клиенты, спонсор, команды заказов, логистики, платежей и аналитики. Поддержка разбирает отклонения. Эксплуатация отвечает за работу инфраструктуры. Внешние партнёры задают ограничения интеграций |
| Основные функции | Расчёт цены и промо, создание заказа, резервирование, выбор доставки, создание платёжной сессии, статусы и отчётность. Есть повторная обработка и ручные действия |
| Требования к качеству | Устойчивость на пиках, приемлемое время ответа, согласованные состояния и прослеживаемая история. Изменения должны выходить предсказуемо. Численные показатели не согласованы |
| Окружение | Интернет-магазин, мобильные каналы, маркетплейсы, платёжные провайдеры, службы доставки, склады и BI. Промо и наличие вызываются как зависимости. Их точное размещение нужно уточнить |
| Основные части | Java-монолит управляет заказом. Oracle хранит данные, правила и интеграционные таблицы. Вокруг работают .NET-интеграции, Python-аналитика, очереди, batch-задания и административные инструменты |
| Сложившиеся решения | Новые сценарии добавлялись отдельными ветками. Правила распределены между кодом, БД и настройками. Используются синхронные вызовы, очереди и обмен через таблицы. По словам техлида, резервный расчёт промо не всегда даёт тот же результат |
| Технологии и ограничения | Java, Oracle, .NET и Python. Собственный дата-центр, ограниченная виртуализация и почти исчерпанные мощности. Десятки терабайт данных, неполное архивирование. Бизнес нельзя останавливать, развитие функций должно продолжаться |
| Риски и неизвестное | Общая БД связывает компоненты и совмещает операционную нагрузку с отчётами. Статусы меняются в нескольких местах. При повторах бывают дубли логистических заявок. Сквозную историю трудно восстановить. Полной карты зависимостей и замеров нет |

## Что сильнее всего ограничивает изменения

| Проблемная зона | Следствие |
| --- | --- |
| Оформление, цена и промо | Изменение правила может затронуть несколько каналов и замедлить оформление |
| Oracle и общие таблицы | Выделение сервиса не убирает зависимость от БД. Перед заменой Oracle нужно найти процедуры и всех потребителей таблиц |
| Статусы, повторы и ручные действия | Изменение процесса может нарушить восстановление заказов и работу поддержки |
| Аналитика | Тяжёлые выборки мешают операциям. Разные трактовки отмен, возвратов и скидок дают разные показатели |
| Инфраструктура | Нагрузку нельзя быстро компенсировать добавлением мощностей |

## Что ещё нужно уточнить

| Недостающие данные | У кого уточнить |
| --- | --- |
| SLA/SLO, допустимые окна работ и условия отката | Бизнес, владельцы процессов и эксплуатация |
| RTO/RPO, порядок восстановления и сверки заказа с оплатой и доставкой | Эксплуатация, заказы, платежи и логистика |
| RPS/TPS, p95/p99, профиль пиков и запас мощностей | Техлид и эксплуатация |
| Допустимая задержка статусов и отчётов, правила консистентности | Заказы, поддержка, платежи и аналитика |
| Правила работы при недоступности промо, наличия, оплаты и доставки | Бизнес и владельцы соответствующих процессов |
| Полная карта интеграций, границы сервисов и потребители Oracle | Техлид, логистика и аналитика |

Через три месяца нужна проверенная картина текущего состояния и основа перехода. Через год планируется запуск новых сервисов. Постепенный отказ от Oracle должен учитывать эти цели и непрерывность операций.
